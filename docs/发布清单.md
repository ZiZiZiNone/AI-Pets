# 发布清单（2.1.0）

发版前照着跑一遍。每一段都写清了**怎么跑**、**通过了意味着什么**、**失败意味着什么**。

- 所有命令在仓库根目录 `E:\AI\AI-Pets` 下用 **PowerShell** 执行。
- 本清单里的每条命令、每个路径都对着工作树核对过；核对结果写在每行的「现状」列。
- `2.1.0` 是本轮计划发布的版本号；**版本号由主控统一改**，本清单只负责核对三处是否一致。

## 0. 先决条件

### 0.1 工具链

| 依赖 | 要求 | 核对方式 |
| --- | --- | --- |
| Node.js | 22 或更高（`.nvmrc` 与 `package.json` 的 `engines` 都锁 22，与 CI 一致） | `node -v` |
| Rust | `stable`，由根目录 `rust-toolchain.toml` 固定（自带 `clippy` 与 `rustfmt`） | `cargo --version` |
| 链接器 | MSVC Build Tools（CI 走这条），**或** MinGW-w64 的 `gcc`（本机走这条） | 见 0.2 |
| Python | 3.x，供探针与协议脚本使用 | `python --version` |
| PyYAML | 可选。`doctor.py` 没装就退回内置的最小解析器，输出里会写明用的哪一种 | `python -c "import yaml; print(yaml.__version__)"` |

### 0.2 环境变量（本机走 GNU 路线时**必须**先设）

`npm run verify` 内部调的是 `cargo`，**不带 `+工具链`**，所以不走 MSVC 时必须用环境变量
把它切过去，否则它会按 `rust-toolchain.toml` 解析出 `-msvc` 然后卡在链接上。
**每个新开的 PowerShell 窗口都要重新设一遍。**

```powershell
$env:RUSTUP_TOOLCHAIN = 'stable-x86_64-pc-windows-gnu'
$env:CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER = 'E:\AI\mingw64\mingw64\bin\gcc.exe'
$env:PATH = 'C:\Users\A\.cargo\bin;E:\AI\mingw64\mingw64\bin;' + $env:PATH
```

设完先确认一遍：

```powershell
rustc --version; gcc --version
```

| 通过标准 | 失败意味着 |
| --- | --- |
| 两行版本号都打出来，没有 `linker not found` / `command not found` | 工具链没装好，或 MinGW 路径写错。MinGW 目录里要有 `gcc` / `dlltool` / `ar` |

> 想少占系统盘的话，可以再加 `$env:CARGO_TARGET_DIR = 'E:\AI\AI-Pets-target'`。

### 0.3 执行顺序（**顺序错了会误判**）

```text
npm.cmd run build        → 产出 dist/
        ↓
cargo build --release …  → 产出内嵌这份 dist/ 的 ai-pets.exe
        ↓
npm.cmd run verify       → 取证（会检查 exe 是否比 dist/ 新）
        ↓
实机探针                 → 全部跑在刚刚构建出的 release 二进制上
```

- `verify` 找不到 release 二进制会直接失败（`release binary not found`）。
- `verify` 发现 exe 比 `dist/` 旧会报 **STALE BINARY** 并失败——那说明构建顺序反了。
- 四个 GUI 探针跑的都是 `src-tauri/target/release/ai-pets.exe`，**不是 dev server**。
  没出 release 二进制，探针会直接报 `the release binary is missing` 并退出 1。

| 4 | `npm.cmd run build` | 等于「类型检查 + 死导出扫描 + 导入环扫描 + 生产构建」，`dist/` 生成成功 | 三个门任一失败，或前端构建失败 | ✅ 存在 |

| 7 | `cargo test --manifest-path src-tauri/Cargo.toml --features custom-protocol` | Rust 单测全绿（令牌、鉴权闸门、动作白名单、权限表、Win32 标志位等） | 有单测挂了 | ✅ CI 里有同一条 |
| 8 | `cargo build --release --features custom-protocol --manifest-path src-tauri/Cargo.toml` | `src-tauri/target/release/ai-pets.exe` 生成，且内嵌的是第 4 步那份 `dist/` | 没带 `custom-protocol` 的话，窗口会指向 Vite dev server，装完白屏 | ✅ 命令有效（特性名与 `tauri.conf.json` 对得上） |
| 9 | `npm.cmd run verify` | 七项取证全过：PE 取证 / 工作树比对 / 产物残留 / 死导出 / 导入环 / Rust 三门 / 逐文件 diff；并重新生成 `docs/VERIFICATION.md` | 报告里会写明是哪一项没过。**没跑第 8 步会直接报 `release binary not found`；exe 比 `dist/` 旧会报 STALE BINARY** | ✅ 存在 |

```powershell

npm.cmd run scan:dead
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --features custom-protocol -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --features custom-protocol
cargo build --release --features custom-protocol --manifest-path src-tauri/Cargo.toml
npm.cmd run verify
```

> 注意：第 4 步 `npm.cmd run build` 已经包含类型检查、死导出扫描与导入环扫描，
> 上面单列 1–3 是为了早失败、少等一次构建。

## 3. 发布动作

### 3.1 版本号：**三处必须一致**

| 位置 | 字段 | 当前值 | 本轮目标 |
| --- | --- | --- | --- |
| `package.json` | `version` | `2.0.1` | `2.1.0` |
| `src-tauri/Cargo.toml` | `version` | `2.0.1` | `2.1.0` |
| `src-tauri/tauri.conf.json` | `version` | `2.0.1` | `2.1.0` |

改完用这条命令核对，**三行必须一样**（这条只读「本包自己的」版本号，
不会误命中 `Cargo.toml` 里依赖项的 `version = "…"`）：

```powershell
(Get-Content package.json -Raw          | ConvertFrom-Json).version
(Get-Content src-tauri\tauri.conf.json -Raw | ConvertFrom-Json).version
(Select-String -Path src-tauri\Cargo.toml -Pattern '^version\s*=' | Select-Object -First 1).Line
```

| 通过标准 | 失败意味着 |
| --- | --- |
| 三行都是 `2.1.0` | 漏改一处 → 安装包文件名、程序「关于」页、npm 包版本会互相打架 |

> 改完版本号后要**重新跑第 8 步**（`cargo build --release …`），
> 否则 `ai-pets.exe` 里还是旧版本号，探针和安装包都会带着旧版本。

### 3.2 提交与打标签

```powershell
git add -A
git status --short            # 确认没有意外文件进来
git commit -m "release(app): 2.1.0 应用全面升级"
git push origin main
git tag v2.1.0
git push origin v2.1.0
```

| 检查 | 通过标准 |
| --- | --- |
| 标签打在**打了新版本号的提交**上 | `git show v2.1.0 --no-patch` 里的 commit 与 `git rev-parse HEAD` 一致 |
| 标签推上去了 | `git ls-remote --tags origin` 能看到 `refs/tags/v2.1.0` |

> 提交信息按项目约定写成 `type(scope): 一句中文总结`，**不写正文**。

### 3.3 Release 会自动发生什么

`.github/workflows/release.yml` 在 **`windows-latest` runner** 上跑（该 runner 预装 MSVC
Build Tools，所以产出的就是「标准构建」）：

1. `npm ci --no-audit --no-fund`
2. `npm run tauri build` —— Tauri 会先跑 `beforeBuildCommand`（即 `npm run build`），
   再编译并打包。`custom-protocol` 特性由 Tauri CLI 自动带上，**缺失会导致装完白屏**。
3. 收集安装包，**两个都必须有**，少一个就直接失败：
   - `bundle/msi/*.msi` → `AI-Pets_2.1.0_x64_en-US.msi`
   - `bundle/nsis/*.exe` → `AI-Pets_2.1.0_x64-setup.exe`
4. `gh release create` 创建 GitHub Release 并上传两个附件，标题 `AI-Pets v2.1.0`。

| 安装包 | 安装范围 | 管理员权限 | 给谁 |
| --- | --- | --- | --- |
| `AI-Pets_2.1.0_x64-setup.exe`（NSIS） | 当前用户，装到 `%LOCALAPPDATA%` | **不需要** | **普通用户选这个** |
| `AI-Pets_2.1.0_x64_en-US.msi`（MSI） | 全机（per-machine） | 需要提权；`msiexec /qn` 返回 `1603` / `Error 1925` 属预期 | 需要全机部署的场合 |

> 手动触发工作流时（`workflow_dispatch`），输入框里的默认标签仍是旧版本号，
> **要改成 `v2.1.0`** 再触发。

### 3.4 发完要核对什么

### 3.5 回滚

| 情况 | 怎么办 |
| --- | --- |
| **标签打错了 / 想撤回这个版本** | 删标签再推：`git tag -d v2.1.0` → `git push origin :refs/tags/v2.1.0`（GitHub 上的 Release 不会自动跟着删，需要手动在 Release 页面删掉） |
| **想把标签挪到另一个提交** | `git tag -f v2.1.0 <目标提交>` → `git push origin -f v2.1.0`；再到 Release 页面把 Release 的 target 改成同一个提交，重新跑一次工作流 |
| **Release 里附件坏了 / 构建失败了** | Release 工作流支持手动重跑：在 Actions 页面找到该次运行 → Re-run all jobs。**不需要改代码，也不需要删标签。** |
| **版本本身有问题，必须撤回** | 删标签 → 把 `main` 回退到出问题的提交之前 → 推 `main`。**已装到用户机器上的旧版本不受影响**（安装包不会自动更新），要撤得靠新版本覆盖。 |

> **先看清楚再撤**：GitHub Release 已经被别人下载过之后，删标签只是让页面消失，
> 已经下载的安装包照样能用。撤版本之前先确认是不是只要重跑构建就能解决。
