# 发布清单

发版前跑一遍。**机器能判定的部分已经做成一条命令**：

```powershell
python scripts\release-check.py        # 或：npm.cmd run release:check
```

它会按下面的顺序把 §0~§3 的门与探针全跑一遍，给出总表，退出码 **0 = 全绿 / 1 = 有门没过 /
2 = 有检查因为不在实机测试时间窗里没执行**。

```powershell
python scripts\release-check.py --dry-run   # 只列出要跑什么，一条都不执行（不会开窗口）
python scripts\release-check.py --self-test # 只跑脚本自己的自检（时间窗边界、清单、探针是否还在）
```

本文档说明每一步**在验什么**、**失败了意味着什么**，以及哪几步**必须由人来做**。

- 所有命令在仓库根目录 `E:\AI\AI-Pets` 下用 **PowerShell** 执行。
- **版本号不写死在这份文档里**：所有「本轮目标版本」一律读 `package.json` 的 `version`，
  改版本号的地方只有三处（§3.1）。
- 跑 `release-check.py` 之前不需要手动设 Rust 的环境变量——脚本会自己找工具链的家、
  自己选链接路线，并把结论打印在开头（§0.2 只在你**手动**敲 cargo 时才需要）。

## 0. 先决条件

### 0.1 工具链

| 依赖 | 要求 | 核对方式 |
| --- | --- | --- |
| Node.js | **22 或更高**（`package.json` 的 `engines` 写的是 `>=22`；`.nvmrc` 与 CI 都锁 22） | `node -v` |
| Rust | `stable`，由根目录 `rust-toolchain.toml` 固定（自带 `clippy` 与 `rustfmt`） | `cargo --version` |
| 链接器 | MSVC Build Tools（CI 走这条），**或** MinGW-w64 的 `gcc`（本机走这条） | 见 0.2 |
| Python | 3.x，供探针与协议脚本使用 | `python --version` |
| PyYAML | 可选。`doctor.py` 没装就退回内置的最小解析器，输出里会写明用的哪一种 | `python -c "import yaml; print(yaml.__version__)"` |

> Rust 工具链已经搬到 E 盘：`CARGO_HOME = E:\AI\cargo`、`RUSTUP_HOME = E:\AI\rustup`
> （`C:\Users\A\.cargo` 与 `C:\Users\A\.rustup` 已不存在）。**新开的 PowerShell 窗口默认
> 找不到 cargo**，这会让所有 Rust 门瞬间变红——`release-check.py` 会自己找（§0.2）。

### 0.2 环境变量（**手动敲 cargo 时**才需要设）

```powershell
$env:CARGO_HOME = 'E:\AI\cargo'
$env:RUSTUP_HOME = 'E:\AI\rustup'
$env:RUSTUP_TOOLCHAIN = 'stable-x86_64-pc-windows-gnu'
$env:CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER = 'E:\AI\mingw64\mingw64\bin\gcc.exe'
$env:PATH = 'E:\AI\cargo\bin;E:\AI\mingw64\mingw64\bin;' + $env:PATH
```

设完先确认一遍：

```powershell
cargo --version; rustc --version; gcc --version
```

| 通过标准 | 失败意味着 |
| --- | --- |
| 三行版本号都打出来，没有 `linker not found` / `command not found` | 工具链没装好，或路径写错。MinGW 目录里要有 `gcc` / `dlltool` / `ar` |

> 本机**没有** Visual Studio，所以 MSVC 路线走不通（`stable-x86_64-pc-windows-msvc` 装了，
> 但没有 `link.exe`）。`release-check.py` 会自动切到 MinGW 路线；cargo 步骤失败时它还会
> 换一次路线重试——链接器找错是最容易修的一种失败，不该因此把整道门判红。

### 0.3 执行顺序（**顺序错了会误判**）

```text
npm.cmd run build        → 产出 dist/
        ↓
cargo build --release …  → 产出内嵌这份 dist/ 的 ai-pets.exe
        ↓
npm.cmd run verify       → 取证（会检查 exe 是否比 dist/ 新）
        ↓
实机探针                 → 全部跑在刚刚构建出的 release 二进制上
```

- `verify` 找不到 release 二进制会直接失败（`release binary not found`）。
- `verify` 发现 exe 比 `dist/` 旧会报 **STALE BINARY** 并失败——那说明构建顺序反了。
- 五个 GUI 探针跑的都是 `src-tauri/target/release/ai-pets.exe`，**不是 dev server**。
  没出 release 二进制，探针会直接报 `the release binary is missing` 并退出 1。

## 1. 代码门

全部在仓库根目录跑。第 1~7 条与 CI（`.github/workflows/ci.yml`）用的是同一条命令；
第 8 条对应 Release 工作流里的构建（`npm run tauri build` 会自动带上 `custom-protocol`）。

| # | 怎么跑 | 通过了意味着 | 失败意味着 | 现状 |
| --- | --- | --- | --- | --- |
| 1 | `npm.cmd run scan:dead` | 没有「完全没人引用」的死导出，也没有「只在自己文件里被用、本不该 export」的符号 | 有冗余导出，要么删掉要么去掉 `export` | ✅ `package.json` scripts 里存在 |
| 2 | `npm.cmd run typecheck` | `vue-tsc` 类型检查通过，且没有未使用的局部变量与参数 | 类型写错，或留了没用的变量/参数 | ✅ 存在 |
| 3 | `npm.cmd test` | Vitest 前端单测全绿 | 有单测挂了，**不要**改测试去迁就实现 | ✅ 存在 |
| 4 | `npm.cmd run build` | 等于「类型检查 + 死导出扫描 + 导入环扫描 + 生产构建」，`dist/` 生成成功 | 三个门任一失败，或前端构建失败 | ✅ 存在 |
| 5 | `cargo fmt --manifest-path src-tauri/Cargo.toml --check` | Rust 代码没有格式偏差 | 有格式偏差；`--check` **不会改文件**，要自己 `cargo fmt` | ✅ CI 里有同一条 |
| 6 | `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --features custom-protocol -- -D warnings` | Clippy 零警告（`-D warnings` 把警告当错误） | 有 lint 警告，必须改掉而不是加 `#[allow]` 糊过去 | ✅ CI 里有同一条 |
| 7 | `cargo test --manifest-path src-tauri/Cargo.toml --features custom-protocol` | Rust 单测全绿（令牌、鉴权闸门、动作白名单、权限表、Win32 标志位等） | 有单测挂了 | ✅ CI 里有同一条 |
| 8 | `cargo build --release --features custom-protocol --manifest-path src-tauri/Cargo.toml` | `src-tauri/target/release/ai-pets.exe` 生成，且内嵌的是第 4 步那份 `dist/` | 没带 `custom-protocol` 的话，窗口会指向 Vite dev server，装完白屏 | ✅ 命令有效（特性名与 `tauri.conf.json` 对得上） |
| 9 | `npm.cmd run verify` | 七项取证全过：PE 取证 / 工作树比对 / 产物残留 / 死导出 / 导入环 / Rust 三门 / 逐文件 diff；并重新生成 `docs/VERIFICATION.md` | 报告里会写明是哪一项没过。**没跑第 8 步会直接报 `release binary not found`；exe 比 `dist/` 旧会报 STALE BINARY** | ✅ 存在 |

```powershell
# 一次跑完全部代码门（任一失败立刻停）
$ErrorActionPreference = 'Stop'
npm.cmd run scan:dead
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --features custom-protocol -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --features custom-protocol
cargo build --release --features custom-protocol --manifest-path src-tauri/Cargo.toml
npm.cmd run verify
```

> 注意：第 4 步 `npm.cmd run build` 已经包含类型检查、死导出扫描与导入环扫描，
> 上面单列 1–3 是为了早失败、少等一次构建。
>
> 上面的 cargo 命令在**没设环境变量**的新窗口里会直接报「找不到 cargo」——用
> `python scripts\release-check.py` 就不用管这件事（§0.2）。

## 2. 实机探针

### 2.0 时间窗与焦点约定（**硬约定**）

| 约定 | 内容 |
| --- | --- |
| **允许做实机测试的时间窗** | **00:00~12:00** 与 **13:30~19:00**（节假日除外） |
| 窗口之外 | 只做离线/代码/文档工作，**不启动应用** |
| **绝不允许抢用户前台焦点** | 不得使用 `SetForegroundWindow` / `AttachThreadInput` / Alt 解锁之类的手段把窗口顶到前台 |

- 下面的探针**本身不抢焦点**：它们通过 DevTools 协议派发输入事件，不做 OS 级前台切换。
  但它们会**真的开出窗口**，所以必须在上面的时间窗内跑。
- **发布门会替你守住这条约定**：不在时间窗时，五个 GUI 探针不会执行，脚本以退出码 **2**
  结束——「没跑过的检查」不算绿灯。要在窗口外先跑离线部分，用 `--skip-gui`。
- 五个 GUI 探针开头都会检查有没有已经在跑的 `ai-pets.exe`，**有就先把它关掉**。
  跑之前请先关掉你自己开着的那个应用。
- 一次把必要的轮次跑完，不要反复重跑。
- 需要人工确认的界面（星盘菜单长按、面板各页签），请**你自己点**，不要让脚本去抢你的鼠标。
- **标了「离线」的探针不受时间窗限制**——它们不启动应用。

## 3. 发布动作

### 3.1 版本号：**三处必须一致**

| 位置 | 字段 | 本轮目标 |
| --- | --- | --- |
| `package.json` | `version` | 你要发的下一个版本（**当前值就是 `package.json` 里的 `version`**，本文不写死） |
| `src-tauri/Cargo.toml` | `version` | 与 `package.json` **完全一致** |
| `src-tauri/tauri.conf.json` | `version` | 与 `package.json` **完全一致** |

改完用这条命令核对，**三行必须一样**（这条只读「本包自己的」版本号，
不会误命中 `Cargo.toml` 里依赖项的 `version = "…"`）：

```powershell
(Get-Content package.json -Raw            | ConvertFrom-Json).version
(Get-Content src-tauri\tauri.conf.json -Raw | ConvertFrom-Json).version
(Select-String -Path src-tauri\Cargo.toml -Pattern '^version\s*=' | Select-Object -First 1).Line
```

| 通过标准 | 失败意味着 |
| --- | --- |
| 三行完全一样 | 漏改一处 → 安装包文件名、程序「关于」页、npm 包版本会互相打架 |

> 改完版本号后要**重新跑第 8 步**（`cargo build --release …`），
> 否则 `ai-pets.exe` 里还是旧版本号，探针和安装包都会带着旧版本。

### 3.2 提交与打标签

```powershell
git add -A
git status --short            # 确认没有意外文件进来
git commit -m "type(scope): 一句中文总结"
git push origin main
git tag -a v<版本> -m "release(app): <版本> <一句话>"
git push origin v<版本>
```

| 检查 | 通过标准 |
| --- | --- |
| 标签打在**打了新版本号的提交**上 | `git show v<版本> --no-patch` 里的 commit 与 `git rev-parse HEAD` 一致 |
| 标签推上去了 | `git ls-remote --tags origin` 能看到 `refs/tags/v<版本>` |

> 标签名必须是 `v<版本>`（带 `v` 前缀），否则 `release.yml` 的 `tags: ['v*']` 触发不了。
> 提交信息按项目约定写成 `type(scope): 一句中文总结`，**不写正文**。
> 中文提交信息要用 `git commit -F <utf8 文件>` 写，别直接敲在命令行上（控制台编码会把
> 中文变成乱码）——仓库外的 `E:\AI\pet-factory\commit_repo.py` 就是干这个的。

### 3.3 Release 会自动发生什么

`.github/workflows/release.yml` 在 **`windows-latest` runner** 上跑（该 runner 预装 MSVC
Build Tools，所以产出的就是「标准构建」）：

1. `npm ci --no-audit --no-fund`
2. `npm run tauri build` —— Tauri 会先跑 `beforeBuildCommand`（即 `npm run build`），
   再编译并打包。`custom-protocol` 特性由 Tauri CLI 自动带上，**缺失会导致装完白屏**。
3. 收集安装包，**两个都必须有**，少一个就直接失败：
   - `bundle/msi/*.msi` → `AI-Pets_<版本>_x64_en-US.msi`
   - `bundle/nsis/*.exe` → `AI-Pets_<版本>_x64-setup.exe`
4. `gh release create` 创建 GitHub Release 并上传两个附件，标题 `AI-Pets v<版本>`。

| 安装包 | 安装范围 | 管理员权限 | 给谁 |
| --- | --- | --- | --- |
| `AI-Pets_<版本>_x64-setup.exe`（NSIS） | 当前用户，装到 `%LOCALAPPDATA%` | **不需要** | **普通用户选这个** |
| `AI-Pets_<版本>_x64_en-US.msi`（MSI） | 全机（per-machine） | 需要提权；`msiexec /qn` 返回 `1603` / `Error 1925` 属预期 | 需要全机部署的场合 |

> 手动触发工作流时（`workflow_dispatch`），输入框里的默认标签仍是旧版本号，
> **要改成 `v<版本>`** 再触发。

#### 安装包体积：现在为什么是 220MB 上下

本地 `npm run tauri build` 的实测（2026-10-24）：MSI **231MB**、NSIS **228.5MB**；
GitHub 上 v2.1.0 的实际附件是 **226.5MiB / 227.7MiB**。

体积几乎全是 300 只宠物的 PNG 素材（`pets/` 共 225MB）。exe 本身只有 **24MB**：
素材**不再内嵌进 exe**（`vite build` 不再把 `pets/` 镜像进 `dist/`），运行时从安装目录读——
以前素材存了两遍（exe 内 226MB + 安装目录 225MB），现在只存一遍。

**下一轮该做的事**：把宠物素材从 PNG 转成 WebP。同样的画面，PNG 平均 700KB/只，
WebP 通常能降到原来的 15%~30%，安装包预计降到 **60MB 上下**。
要注意两件事：一是转换要落在工厂的打包流水线里（`assemble.py` / `strip_build.py`），
否则下次同步素材会退回 PNG；二是转换后要重画一遍验收图，确认深色渐变没出现色带。

### 3.5 回滚

| 情况 | 怎么办 |
| --- | --- |
| **标签打错了 / 想撤回这个版本** | 删标签再推：`git tag -d v<版本>` → `git push origin :refs/tags/v<版本>`（GitHub 上的 Release 不会自动跟着删，需要手动在 Release 页面删掉） |
| **想把标签挪到另一个提交** | `git tag -f v<版本> <目标提交>` → `git push origin -f v<版本>`；再到 Release 页面把 Release 的 target 改成同一个提交，重新跑一次工作流 |
| **Release 里附件坏了 / 构建失败了** | Release 工作流支持手动重跑：在 Actions 页面找到该次运行 → Re-run all jobs。**不需要改代码，也不需要删标签。** |
| **版本本身有问题，必须撤回** | 删标签 → 把 `main` 回退到出问题的提交之前 → 推 `main`。**已装到用户机器上的旧版本不受影响**（安装包不会自动更新），要撤得靠新版本覆盖。 |

> **先看清楚再撤**：GitHub Release 已经被别人下载过之后，删标签只是让页面消失，
> 已经下载的安装包照样能用。撤版本之前先确认是不是只要重跑构建就能解决。
